## 0. Before you press Record

### Choose your environment

The code uses Python, SQL, managed Delta tables and one managed Unity Catalog volume. It avoids external downloads, package installation, legacy DBFS mounts, RDDs and cloud-account credentials.

For personal learning, Free Edition offers serverless compute with quotas and restricted capabilities. It does not expose every enterprise configuration. Its documentation states that accounts are for non-commercial use. For a monetized course or business production, use an appropriately licensed workspace or clarify applicable terms with Databricks. Do not present this as a guarantee that the whole professional syllabus can be demonstrated on Free Edition. [S1]

The steps below target a serverless-capable workspace with Unity Catalog and usable managed/default storage. A normal Azure Databricks workspace is also suitable if an administrator has provisioned the necessary catalog/storage and you select compatible compute.

**Main path:** create `retail_de_course` in a serverless workspace with default storage.  
**Fallback path:** use an existing permitted catalog and set `CREATE_CATALOG=False` in Cell 01. Keep the isolated schema names `v01_bronze`, `v01_silver`, `v01_gold`.

Do not promise that a plain `CREATE CATALOG` works in every enterprise workspace: those environments may need an administrator-configured storage root. In supported serverless workspaces, Catalog Explorer offers “Use default storage”; the current documentation also supports catalog creation without a LOCATION. [S2]

### Permission requirements

An owner-created personal catalog is the easiest path. In a shared workspace, ask the administrator for the precise privileges needed: catalog use, schema creation or use of pre-created schemas, table creation/modification, volume creation and file read/write. Creating a new catalog needs metastore-level `CREATE CATALOG`. Do not respond to permission errors by granting broad administrator rights. Ownership and inherited privileges can satisfy requirements without individually granting every privilege.

## 2. Concepts and architecture — 05:00–23:00

### 05:00–08:00 — Storage, compute and governance

**Show:** `ARCHITECTURE.html`. Point to the raw files, managed tables and compute/governance notes.

**Say:**

“Keep three questions separate: where are the bytes stored, what executes my code, and who controls access? Storage holds files. Compute executes work. Unity Catalog gives us governed names and access controls for data objects. A notebook is where I develop code; it is not the durable home of my Delta tables.”

**Demonstration:** Open the workspace sidebar and point at Workspace, Catalog and SQL. If Compute or Jobs is visible, point to it. Do not create an unnecessary cluster. Explain that the exact navigation labels can differ by edition.

**Analogy:** “The notebook is my workbench, compute is the worker, the catalog is the organised inventory, and storage holds the actual goods.” Then move back to precise terms; do not extend the analogy into security or execution guarantees.

### 08:00–11:00 — Why this medallion design

**Show:** Follow the visual from landing files to Bronze, then Silver and Gold; also point at the quarantine branch.

**Say:**

“Landing is our file arrival area. Bronze keeps source fields with minimal changes and adds provenance. Silver applies types and business validation. Gold exposes a defined business metric. Those names express responsibilities. Creating three folders does not clean data, enforce access or make a pipeline reliable.”

“The medallion pattern is a design choice, not a requirement that every project must have exactly these three schemas. Today we use schemas to make the boundaries visible. Later, we will add incremental processing and recovery.” [S3]

**Important qualification:** Delta transactions apply to table operations; a sequence of separate notebook writes is not one atomic transaction covering all Bronze, Silver and Gold tables. This first lab is a full-refresh teaching snapshot, not a production append-history implementation.

### 11:00–14:00 — Namespaces and file paths

**Show:** The visual's naming panel.

| Object | Example | Meaning |
|---|---|---|
| Catalog | `retail_de_course` | Course data boundary in this example |
| Schema | `v01_bronze` | A named grouping inside that catalog |
| Table | `retail_de_course.v01_bronze.orders` | Queryable rows with metadata |
| Volume | `retail_de_course.v01_bronze.landing` | Governed file storage object |
| File | `/Volumes/retail_de_course/v01_bronze/landing/video01/input/orders.json` | An actual source file inside the volume |

**Say:** “A schema is often called a database in Spark SQL. It is the middle part of this three-level name. A catalog is not a workspace folder, and a volume is not a table. A JSON file has structured records, but we still govern it as a file until we load records into a table.”

**Ask:** “If I change my current schema to Bronze and query `daily_sales` without qualification, where will the system look?” Save the demonstration for the troubleshooting chapter.

### 14:00–18:00 — Managed versus external tables and volumes

**Show:** This comparison, not a cloud-storage setup screen you cannot execute.

| Choice | Use in this lesson | Design consideration |
|---|---|---|
| Managed table | All Bronze/Silver/Gold tables | Databricks manages the table's storage lifecycle/layout; suitable default for our lab |
| External table | Explain, do not execute in the required lab | Explicit cloud path under configured external storage; dropping registration leaves underlying files |
| Managed volume | JSON landing area | Governed file storage without manually choosing cloud paths |
| External volume | Explain only | Govern an existing external file directory |

Managed table data still lives in cloud object storage; “managed” does not mean in-memory or inside the notebook. External tables are still governed when accessed through Unity Catalog, but direct cloud access needs its own appropriate controls. Avoid claiming all external access must use external tables: managed tables also have supported external access mechanisms. [S4, S5]

**Say:** “We will create managed tables without supplying LOCATION. We will read JSON from a volume and write records into separately managed tables. We will not register a table on a path inside a volume.” [S6]

**Optional explanatory SQL — do not run unchanged:**

```sql

USING DELTA
LOCATION 'abfss://container@account.dfs.core.windows.net/course/external_orders';

An empty path here does not define an order schema; a real demo must provide an existing Delta table or a CREATE TABLE definition. Do not attempt the template during this recording.

### 74:00–77:00 — Environment failures you may encounter

Explain these as troubleshooting guidance, not staged proof of errors you did not see.

| Symptom | Check first | Practical response |
|---|---|---|
| CREATE CATALOG reports missing managed storage | Workspace type and configured catalog storage | Use supported default-storage UI or an administrator-provisioned catalog |
| Permission denied creating schemas/tables | Current principal, catalog use and object privileges | Request the precise missing privileges; use pre-created schemas if required |

## 5. Exam decision points and recap — 77:00–85:00

These are original discussion scenarios, not recalled exam questions. Read each prompt, pause for 5–10 seconds, then explain the decision and why the tempting alternative is weak.

### 77:00–82:00 — Six decision scenarios

1. **The team needs to store raw JSON extracts before parsing. Should it create a table or a volume?**  
   A volume is appropriate for the files. Once parsed into governed rows, create a table. “JSON has columns” is not enough to make a file a registered table.

2. **The project has no requirement for direct control of table files. Managed or external table?**  
   Use managed as the starting choice. Choose external when concrete interoperability/location requirements justify it. Do not assume “production means external.”

3. **An external table is dropped. Are its cloud files deleted by that registration change?**  
   No. Dropping the external-table object removes metadata, not underlying files. Managed objects have a managed lifecycle, including applicable recovery/retention behaviour; do not claim immediate byte deletion on DROP. [S4, S5]

4. **A raw order has a negative quantity. Should the source be overwritten to hide it?**  
   Preserve the original and route the rejected record with a reason. This allows explanation and later reprocessing.

5. **A report table exists in Gold but an unqualified query from Bronze fails. What is the first investigation?**  
   Check current catalog/schema and the fully qualified name before changing permissions or recreating objects.

6. **A business analyst needs to execute SQL against published tables. Which compute interface should you evaluate?**  
   A SQL warehouse. A mixed Python/SQL development notebook has different execution requirements. Exact size/cost is a separate workload decision.

**One trap worth emphasising:** A managed table and an external table can both use Delta. Table format and storage-management type are separate dimensions.

## Cell 04 — Generate deterministic synthetic source data
10 customers, 5 products, 20 distinct valid orders, 1 exact duplicate and 2 invalid orders.
The source deliberately uses strings for order fields. Only synthetic data is used.
No Faker installation, external download or cloud credentials are required.


```python
import json
from datetime import date, timedelta

customers = [
    {"customer_id": f"C{i:03d}", "customer_name": f"Demo Customer {i:02d}",
     "city": ["Delhi", "Pune", "Bengaluru"][(i-1) % 3]}
    for i in range(1, 11)
]
products = [
    {"product_id": f"P{i:03d}", "product_name": f"Demo Product {i:02d}",
     "category": "Accessories", "unit_price": str(i * 100)}
    for i in range(1, 6)
]
orders = []
for i in range(1, 21):
    product_no = (i - 1) % 5 + 1
    orders.append({
        "order_id": f"O{i:04d}",
        "customer_id": f"C{(i-1) % 10 + 1:03d}",
        "product_id": f"P{product_no:03d}",
        "order_date": str(date(2026, 9, 1) + timedelta(days=(i-1)//10)),
        "quantity": str((i - 1) % 3 + 1),
        "unit_price": str(product_no * 100),
        "status": "CANCELLED" if i % 5 == 0 else "COMPLETED",
    })
orders.append(dict(orders[0]))
orders.append({**orders[1], "order_id": "O9001", "quantity": "-2"})
orders.append({**orders[2], "order_id": "O9002", "customer_id": None})

for name, records in [("customers", customers), ("products", products), ("orders", orders)]:
    path = f"{INPUT_DIR}/{name}.json"
    dbutils.fs.put(path, "\n".join(json.dumps(r) for r in records) + "\n", overwrite=True)
    print(name, len(records), path)
display(dbutils.fs.ls(INPUT_DIR))
print(dbutils.fs.head(f"{INPUT_DIR}/orders.json", 700))
```

## Cell 07 — Create the clean reference tables
Customer and product inputs are controlled fixtures. We assert uniqueness before joining them to orders.


```python
spark.sql(f"""CREATE OR REPLACE TABLE {table(SILVER, 'customers')} USING DELTA AS
SELECT customer_id, customer_name, city FROM {table(BRONZE, 'customers')}""")
spark.sql(f"""CREATE OR REPLACE TABLE {table(SILVER, 'products')} USING DELTA AS
SELECT product_id, product_name, category, CAST(unit_price AS DECIMAL(12,2)) AS unit_price
FROM {table(BRONZE, 'products')}""")
for name, key, expected in [("customers", "customer_id", 10), ("products", "product_id", 5)]:

    assert frame.count() == expected
    assert frame.select(key).distinct().count() == expected
    assert frame.filter(F.col(key).isNull()).count() == 0
print("Reference table checks passed")
```

## Cell 08 — Validate, quarantine and deduplicate orders
TRY_CAST keeps malformed values from crashing the validation query. COALESCE makes NULL validation results invalid.
Quarantine keeps the raw fields and a reason. Exact duplicates are removed across business fields only.
This is NOT latest-record CDC logic: the fixture contains no conflicting versions for one order ID.


```python
spark.sql(f"""CREATE OR REPLACE TEMP VIEW v01_orders_checked AS
WITH typed AS (
  SELECT *,
    TRY_CAST(order_date AS DATE) AS order_date_typed,
    TRY_CAST(quantity AS INT) AS quantity_typed,
    TRY_CAST(unit_price AS DECIMAL(12,2)) AS unit_price_typed
  FROM {table(BRONZE, 'orders')}
)
SELECT *, COALESCE(
  order_id IS NOT NULL AND customer_id IS NOT NULL AND product_id IS NOT NULL
  AND order_date_typed IS NOT NULL AND quantity_typed > 0 AND unit_price_typed > 0
  AND status IN ('COMPLETED', 'CANCELLED'), FALSE) AS is_valid
FROM typed""")
spark.sql(f"""CREATE OR REPLACE TABLE {table(SILVER, 'orders_quarantine')} USING DELTA AS
SELECT *, CASE
  WHEN customer_id IS NULL THEN 'MISSING_CUSTOMER'
  WHEN quantity_typed IS NULL OR quantity_typed <= 0 THEN 'INVALID_QUANTITY'
  ELSE 'OTHER_INVALID_FIELD' END AS rejection_reason
FROM v01_orders_checked WHERE NOT is_valid""")
spark.sql(f"""CREATE OR REPLACE TABLE {table(SILVER, 'orders')} USING DELTA AS
SELECT DISTINCT order_id, customer_id, product_id,
  order_date_typed AS order_date, quantity_typed AS quantity,
  unit_price_typed AS unit_price, status,
  CAST(quantity_typed * unit_price_typed AS DECIMAL(14,2)) AS order_amount
FROM v01_orders_checked WHERE is_valid""")
display(spark.table(table(SILVER, "orders_quarantine")).select("order_id", "quantity", "customer_id", "rejection_reason"))
assert spark.table(table(SILVER, "orders")).count() == 20
assert spark.table(table(SILVER, "orders_quarantine")).count() == 2
assert spark.table(table(SILVER, "orders")).select("order_id").distinct().count() == 20
```

## Cell 09 — Publish business-ready Gold tables
For this teaching model, completed order value = quantity × unit_price, excluding cancelled orders.
It is not payment settlement or accounting revenue: taxes, returns, discounts and payments are not modelled yet.


```python
spark.sql(f"""CREATE OR REPLACE TABLE {table(GOLD, 'daily_sales')} USING DELTA AS
SELECT order_date, COUNT(*) AS completed_orders,
       SUM(order_amount) AS completed_order_value
FROM {table(SILVER, 'orders')}
WHERE status = 'COMPLETED'
GROUP BY order_date""")
spark.sql(f"""CREATE OR REPLACE TABLE {table(GOLD, 'customer_sales')} USING DELTA AS
SELECT c.customer_id, c.customer_name, c.city,
       COUNT(*) AS completed_orders, SUM(o.order_amount) AS completed_order_value
FROM {table(SILVER, 'orders')} o
JOIN {table(SILVER, 'customers')} c ON o.customer_id = c.customer_id
WHERE o.status = 'COMPLETED'
GROUP BY c.customer_id, c.customer_name, c.city""")
display(spark.table(table(GOLD, "daily_sales")).orderBy("order_date"))
display(spark.table(table(GOLD, "customer_sales")).orderBy("customer_id"))
```

## Cell 11 — Reconcile and verify

```python

silver_count = spark.table(table(SILVER, "orders")).count()
quarantine_count = spark.table(table(SILVER, "orders_quarantine")).count()

duplicates_removed = valid_before_dedup - silver_count
assert (bronze_count, silver_count, quarantine_count, duplicates_removed) == (23,20,2,1)
assert bronze_count == silver_count + quarantine_count + duplicates_removed
expected_value = sum(Decimal(r["quantity"]) * Decimal(r["unit_price"])
                     for r in orders[:20] if r["status"] == "COMPLETED")
result = spark.sql(f"SELECT SUM(completed_orders) AS n, SUM(completed_order_value) AS value FROM {table(GOLD, 'daily_sales')}").first()

customer_total = spark.sql(f"SELECT SUM(completed_order_value) AS value FROM {table(GOLD, 'customer_sales')}").first()["value"]
